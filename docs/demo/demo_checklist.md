## ถ้าลูกค้าถาม

- **"ทำไมไม่ใช้ฎีกาเลขนั้น"** → การค้นฎีกาเป็นเวอร์ชันแรก (ค้นจากทั้งคำถาม) — มีแผน V2 ค้นจากหลักกฎหมายแทน (decisions #12) · ระบบอ้างได้เฉพาะฎีกาใน DB
- **"แพรวพราวเข้า ม.119 อนุไหน"** → ในรอบ final ระบบสรุป (1)+(2) — การเลือกอนุมาตราเป็นการวินิจฉัยของ AI ยังไม่มีการตรวจองค์ประกอบรายอนุมาตรา (ผลเงินไม่เปลี่ยน เพราะการเข้า/ไม่เข้า ม.119 ถูกต้อง)
- **"ความแม่นยำเท่าไร"** → holdout 40 ข้อที่ไม่เคยใช้พัฒนา: อ้างมาตราในคอลัมน์ H ครบ 34/40 (85%) เทียบ Gemini อย่างเดียว 18/40 (45%)

## ข้อจำกัดภายใน (ไม่ต้องพูดเชิงเทคนิคกับลูกค้า)

1. **ม.119 อนุมาตรา = LLM judgment** — schema แยก alleged / found และ validation บังคับให้ข้อสรุป/ตารางใช้เฉพาะ found ที่มีจริงใน DB แต่ยังไม่มี per-ground element check → final run ได้ (1)+(2) แทน (2)
2. **Supreme Court retrieval = V1 whole-question** (decision #11) — ฎีกาไม่ซ้ำข้ามประเด็นและต้องผูก/เอ่ยถึงมาตราของประเด็น แต่ยังไม่ใช่ฎีกาที่ตรงหลักที่สุด · V2 = principle query → dense → rerank → validate → dedupe → cite (decision #12)
3. **topic ที่ LLM เขียนอาจไม่ตรง section** — หัวข้อย่อยการปรับบทสร้างจาก section + topic ที่ LLM ให้ (เช่น ม.118 วรรคสอง ได้ topic เรื่องสถานะนายจ้าง/ลูกจ้าง)
4. **ข้อมูลที่ยังไม่มีใน DB** — ป.พ.พ. ลักษณะห้างหุ้นส่วน (ความรับผิดหุ้นส่วนผู้จัดการ), ฎีกา 7780–7782/2556 และฎีกานอกชุดที่ดึงมา
5. **อื่น ๆ** — ตัวหนาภายใน bullet ปรับบท (Point 2) ยังไม่ทำ · คำถามใหม่ ~2.5 นาที/~8 บาท · เครดิต ~290 บาท ไม่พอ test160 (~1,100–1,200 บาท) · ลิงก์ tunnel เปลี่ยนทุกครั้ง
