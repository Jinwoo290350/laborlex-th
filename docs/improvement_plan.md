# แผนปรับปรุง LaborLex-TH — ทุกค่าต้องมีที่มา (2026-10-01)

## หลักการ
1. **ไม่มีค่าที่ตั้งตามความรู้สึก** — ทุกค่าต้องมาจากหนึ่งในห้าแหล่งนี้ และบันทึกไว้ใน registry (`config/params.yaml`) พร้อมหลักฐาน:
   | ประเภท | ความหมาย | ตัวอย่าง |
   |---|---|---|
   | `statute` | อ่านจากตัวบทใน DB | อัตราค่าชดเชย, ÷30 (ม.68) |
   | `requirement` | ข้อกำหนดลูกค้า/rubric/สัญญา | template คำตอบ, ห้ามเดา |
   | `data` | สถิติจากข้อมูลจริง (สูตรคำนวณเก็บในโค้ด) | จำนวนประเด็นสูงสุด, ความยาวตัดข้อความ |
   | `measured` | เลือกจากการทดลองบนชุด **tune** ด้วยเกณฑ์ที่ประกาศก่อนทดลอง | threshold เลือกมาตรา, จำนวนร่าง |
   | `design` | ข้อจำกัดเชิงระบบที่อธิบายได้ (ไม่ใช่การจูน) | temperature 0 เพื่อให้ผลซ้ำได้และ cache ได้ |
2. **ไม่มีการสุ่ม** — แบ่งชุดข้อมูลด้วย hash (md5 ของ id) ไม่ใช่ random · LLM ใช้ temperature 0 + seed คงที่ + cache → รันซ้ำได้ผลเดิม · ทุกผลทดลองบันทึก config hash
3. **ไม่จูนบนชุดที่ใช้รายงานผล** — dev100 แบ่งเป็น **tune 60 / holdout 40** (stratified ตาม category × difficulty, เรียงด้วย md5) · จูนบน tune เท่านั้น · รายงานบน holdout ครั้งเดียวตอนจบ · test160 ไม่แตะ
4. **เกณฑ์ตัดสินประกาศก่อนทดลอง** — เช่น "เลือกค่าที่ PASS สูงสุด ถ้าต่างกันไม่เกิน 1 ข้อให้เลือกค่าที่ถูกกว่า" · ชุดเล็ก (20–60 ข้อ) ความต่างที่เชื่อได้ต้องผ่าน paired test (McNemar) — ถ้าไม่ผ่าน ถือว่า "ไม่ต่าง" และเลือกตัวที่ถูก/ง่ายกว่า
5. **ตัววัดสองชั้นเสมอ** — PASS จาก judge (ต้อง calibrate ก่อน) + ตัววัดที่ไม่ใช้ judge (มาตราในเฉลยที่คำตอบอ้าง, citation ผิด = 0)

## ลำดับงาน (ผลกระทบต่อบาท สูง → ต่ำ)

**ขั้น A — ฟรี (ไม่เรียก Gemini)**
1. สร้าง `config/params.yaml` + โหลดในโค้ด + test ที่ fail ถ้าค่าใดไม่มี `source`/`evidence`
2. แบ่ง dev100 → tune 60 / holdout 40 ด้วย md5 (บันทึกรายชื่อไว้ใน repo)
3. แก้ค่าประเภท `data` ทั้งหมด (ตัดข้อความ, ความยาวคำถาม, คดีแบบ overlap)
4. จูน retrieval ทั้งหมดด้วย Recall@k บน tune (RRF k, pool, โควตา, วรรคต่อมาตรา) → รายงานเส้นโค้งใน `docs/results/`
5. วิเคราะห์ log จากรันที่มีแล้ว (12 ข้อ): p ของ ⑤, คะแนน verify → ค่าเริ่มต้นของ threshold

**ขั้น B — calibrate judge (~35 บาท)**
6. judge ตรวจคำตอบ baseline 90 แถว (30 ต่อโมเดล, stratified) → Cohen's κ ต่อเกณฑ์ + PASS agreement
   - เกณฑ์ยอมรับ: κ ≥ 0.6 ต่อเกณฑ์ และ PASS agreement ≥ 80% · ถ้าไม่ถึง ปรับ prompt judge แล้ววัดซ้ำบน **อีก 90 แถวที่ไม่เคยใช้** (มี 300 แถว พอสำหรับ 3 รอบ)

**ขั้น C — จูนบน tune (~200 บาท)**
7. รัน tune 20 ข้อ (stratified) ด้วย config ปัจจุบัน → เก็บ p ⑤ + คะแนน verify + ผล judge → เลือก threshold ⑤ และ revise
8. ablation ที่เหลือเฉพาะที่คาดว่าเปลี่ยนผล (few-shot 0/2, thinking) — ข้ามถ้างบไม่พอ

**ขั้น D — ฎีกา (ฟรีถึงถูก)**
9. ทดลอง iApp Deka API / ไฟล์ citation HF (CC-BY) กรองคดีแรงงาน → ingest พร้อมป้ายศาล · กติกาคดีแบบ overlap เหมือนข้อ 3

**ขั้น E — วัดผลจริงครั้งเดียว (~230 บาท)**
10. freeze config → รัน holdout 40 ข้อ → รายงานพร้อม κ ของ judge และตัววัดที่ไม่ใช้ judge

## งบประมาณ — ต้องตัดสินใจ
- งานข้างบนรวม ≈ 35 + 200 + 230 ≈ **470 บาท** จากที่เหลือ ~860
- **แต่รัน test160 (เฟส 2) เองใช้ ≈ 160 × 4.5 ≈ 720 บาท** (ไม่มี judge) → เครดิตที่เหลือไม่พอทั้งสองอย่าง
- ทางเลือก: (ก) เติมเครดิตก่อนเฟส 2 (ข) ใช้ Batch API ตอนรัน test160 (ครึ่งราคา ≈ 360 บาท) — ต้องทดสอบว่าได้ผลเท่ากัน (ค) ลดขั้น C
